# RVA 009B6080 static sorted insertion

The new hypothesis is that a static C++ insertion helper compiled with the integration entry in Open BFME 2's `Code/Libraries/Source/VP6/Rva001C6980InsertSorted.cpp` at game.dat RVA 001C6980 reproduces MSVC 7.1's private ESI/EDX convention. A measured mismatch, or an emitted helper expecting different incoming registers or stack arguments, would refute it. No original vendor class, external cdecl contract or exported function identity is proposed. The helper retains the BFME 1 address in its name and remains static.

The complete retail decode is `build/vp6-donor-run/009b6080-decode.txt`. Its two complete return paths end at 009B60C8 and 009B60D7; INT3 padding begins at 009B60D8. All branches target instructions inside [009B6080, 009B60D8). There are no direct calls, indirect calls, tail jumps, exception handlers or cleanup helpers. The conditional EBP save has a corresponding pop before both result paths; EBX and EDI are restored on both exits. ESI is read but never written, so it needs no save and restore in the helper.

On entry ESI is the array base, EDX is the insertion index and entry ESP+4 is an `int *` head argument. The body scales both the insertion index and the current list index by 12, reads signed weights at +4 and reads or writes signed successor indices at +0 with -1 as the terminal marker. It compares weights with signed JLE and places a new entry before equal weights. On the head path it writes the insertion index through the head pointer; on the other path it writes through the predecessor's successor field. Both paths store the stopping index into the inserted entry's successor field and return without stack cleanup. EDX is scratch on exit, and no return value is required. The source leaves the four bytes at entry +8 opaque because this helper never reads or writes them. The complete builder 009B60E0 independently contains the same sorted-insert algorithm twice on 12-byte next/weight/packed-edge records.

The generated static helper emits the complete 88 bytes identically with no relocation fields. The object and complete object decode are retained as `build/vp6-donor-run/009b6080-donor-02.obj` and `009b6080-object-abi.log`. The integration entry's complete 24-byte decode loads its third argument as the stack head pointer, its second argument into EDX and its first argument into ESI, saves and restores ESI around the helper call and performs four-byte stack cleanup. This confirms the compiler's argument-to-register mapping without an assembly adapter. The integration entry is annotated absent-from-retail and owns no ledger row.

No retail direct caller was found. The broad raw E8/E9 scan finds zero candidate sites in `.text` (`009b6080-raw-reference-screen.log`), so there is no caller hit requiring instruction-boundary validation. The relocation-directory search also finds zero HIGHLOW references to the helper's VA (`009b6080-relocated-address-refs.log`). `callers_of.py` independently reports no named direct caller (`009b6080-callers-screen.log`). These observations do not identify a native owner or prove a public source declaration; the recovery claims only this complete address-derived static body and its decoded private contract.

The first port and the final port both emit exactly 88 bytes; the second only corrects the integration-entry spelling and its annotation. Raw probes are `build/vp6-donor-run/009b6080-donor-01-probe.log` and `009b6080-donor-02-probe.log`. ILT oracle reports UNTESTABLE for this static library address, not CONTRADICTED. No new symbol pin is needed because the helper has TU-local linkage. Scoped byte verification is retained in `build/vp6-donor-run/009b6080-add-match.log`.
