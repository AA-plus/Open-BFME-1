# Win32BIGFileSystem directory loading at RVA 0x009CDB90

The reconstruction matches the complete 459-byte retail body, including relocation targets, in `game/GameEngineDevice/Source/Win32Device/Common/Win32BIGFileSystem_loadBigFilesFromDirectory.cpp`. Verification used base revision `4fcde49dfc9f5f530730af7a0772ae071135fa4a` with the local conversion applied. No header, shim, pin, policy or tool was changed.

## Experiment and refutation

The original bank reproduces at 459 bytes with 19 relocation slots and 13 differing bytes. Retail loads the filename-set count before reserving and constructing the by-value resize argument. The bank constructs that argument before loading the count. The differences occupy offsets `+0xA9`, `+0xAA`, `+0xAB`, `+0xAC`, `+0xAE`, `+0xAF`, `+0xB0`, `+0xB1`, `+0xB2`, `+0xB3`, `+0xB4`, `+0xB5` and `+0xB6`. The rest of the body already matches.

The successful hypothesis was that the one-argument resize forwarding overload needs the canonical `AsciiString` declaration, rather than the historical `Common/AsciiString.h` shim selected by the bank. The canonical class inherits from `StringBase<char>` and forwards construction and destruction through that base. The vendored STLport `_vector.h` itself defines `resize(size_type n) { resize(n, _Tp()); }`. The reconstruction retains the established Q3SortElem4 ABI bridge and uses that forwarding form. The hypothesis would fail if construction order remained different, register allocation elsewhere changed, cleanup ownership changed, or strict relocation verification rejected any target.

## Identity and complete boundary

The complete decode begins with the exception-registration prologue at RVA 0x009CDB90 and ends with `ret 0xC` at RVA 0x009CDD58. Five following bytes are INT3 padding. There is one ordinary return, no outgoing conditional branch, and no tail jump from this body. All conditional paths rejoin its cleanup and epilogue.

The decoded constructor at RVA 0x009CC350 installs vtable VA 0x01143B40 after calling the archive-filesystem base constructor. Slot 9 of that table contains VA 0x00DCDB90. The independently matched `Win32BIGFileSystem::init` body at RVA 0x009CC590 constructs the empty directory and `*.big` mask, passes the overwrite argument, and calls slot `+0x24`. Zero Hour's `GeneralsMD/Code/GameEngineDevice/Source/Win32Device/Common/Win32BIGFileSystem.cpp` defines the corresponding `loadBigFilesFromDirectory` operation. BFME additionally copies the filename set into a vector, sorts it, and deletes an existing mapped archive before replacement. The donor function has no source comments inside this body to carry over.

The owning name would be refuted by a different decoded vtable target, a caller argument setup inconsistent with the directory and mask parameters, or evidence that the matched init identity belongs to another operation. The target's Bool ABI comes from its byte return in AL and the canonical Bool definition, not the older init shim's unused integer return declaration. Q3SortElem4 and Q3SortCompare remain the bank's established opaque spellings; no source identity is asserted for the sort driver beyond its address-derived name.

## Container fields and ownership

The filename list is a set of one-pointer AsciiString values. Its actual virtual filling call reaches slot 5 of the Win32LocalFileSystem table at VA 0x01143B98, whose target is RVA 0x009CE190. That complete 974-byte body constructs strings from the directory and filenames and reaches find and insert through ILT routes 0x00039103 to 0x00195EC0 and 0x000033AF to 0x00197270. Complete insert_unique decoding reaches `_M_insert` through 0x00012CAB to 0x00195D30. Both insertion paths construct the node value through 0x00007554 to 0x000620B0. The entire 66-byte construction helper passes destination and source to the 121-byte StringBase copy constructor at RVA 0x00887B60 and accesses no second value field. That constructor reads the source pointer at offset zero, stores it at destination offset zero, and increments the pointed buffer's reference count. The case-insensitive comparator is witnessed by the complete insert and find bodies' `_memicmp` route and the complete 91-byte compareNoCase body at RVA 0x00090570. Node allocation size is corroboration only.

The target's actual set-to-vector copy helper at RVA 0x009CC4C0 is completely decoded, including both returns. It passes each node's value at offset 0x10 to StringBase::set at RVA 0x00887C90 and advances the output by four bytes. The full 135-byte set helper compares object addresses, releases the old buffer, copies the single pointer, and increments its reference count. Its normal `ret 4` and conditional tail transfer to LeaveCriticalSection both consume the one pointer argument. No second payload field is read or written. The vector destructor at RVA 0x000658A0 walks in four-byte steps, releases every value through RVA 0x00887940, and frees the three-pointer vector's storage through the decoded allocation routes.

The archive map contains `pair<const AsciiString, ArchiveFile *>`. The target independently reads the mapped pointer at node offset 0x14, invokes its virtual deleting destructor, then stores the newly returned ArchiveFile pointer through the mapped reference returned by operator[]. The entire 169-byte operator[] body at RVA 0x00063960 returns node offset 0x14 on both paths and constructs the missing entry from a copied key and a zero mapped pointer. Its actual insertion follows ILT 0x0000A529 to the complete 629-byte hinted insert at RVA 0x000633E0. Every inserting path reaches RVA 0x00063140 through ILT 0x000235B5, either directly or through the complete 310-byte unhinted insert at RVA 0x00063230 (ILT 0x00039B85). Both branches of RVA 0x00063140 reach the placement constructor through ILT 0x00005E4D to RVA 0x00062900. The entire 79-byte pair construction helper calls the StringBase copy constructor for field zero and copies `[source+4]` to `[destination+4]`. This establishes both fields independently of the 24-byte node allocation and existing template names. The complete map-find body at RVA 0x009C9B70 and comparator at RVA 0x0005FEB0 agree with the same key placement.

The existing ledger names RVA 0x000633E0 as a DetailedArchivedDirectoryInfo instantiation. That name does not establish this caller's payload: its decoded insertion routes and actual pair constructor copy an ArchiveFile pointer. This reconstruction uses the witnessed pointer map and makes no identity claim for that helper. The existing helper source and ledger identity are outside this assignment. The full intermediary bodies, comparator at RVA 0x00062FA0, and ILT routes are retained in build/009cdb90-resume/decoded-additional.log and build/009cdb90-resume/decoded-map-routes.log, with checked-callee outputs in build/009cdb90-resume/checked-<eight-digit-rva>.log.

## Calls and exception cleanup

The target is __thiscall with receiver ECX, two four-byte owning string arguments and one Bool argument occupying a four-byte stack slot. It destroys both strings before returning AL and popping 12 bytes. The decoded init caller supplies these arguments in the matching order. The local-filesystem virtual call supplies five stack arguments and its complete target returns with `ret 0x14`; the recursion flag is read as a byte. The archive-open virtual call supplies a C-string pointer and the complete 832-byte target at RVA 0x009CC710 returns a pointer in EAX and pops four bytes on both return paths. The load-directory virtual call supplies archive pointer, filename reference and Bool; the complete 898-byte target at RVA 0x009CACF0 returns with `ret 0xC`. The main receiver is unadjusted and its archive map is accessed at receiver offset 0x04.

The deleted mapped value is called through virtual slot zero with flag 1. The complete ArchiveFile deleting destructor at RVA 0x009D0C30 tests bit zero of its four-byte flag, invokes destruction and optional deallocation, returns the receiver in EAX and pops four bytes. The actual archive-open body constructs Win32BIGFile through RVA 0x009D14E0. That complete constructor installs vtable VA 0x01143BE8, whose slot zero leads to RVA 0x009D17F0. Its complete 30-byte deleting destructor has the same flag-one ABI and reaches global delete at RVA 0x00881EB0. Its complete destructor at RVA 0x009D1500 releases the owning strings at receiver offsets 0x28 and 0x24 before calling the ArchiveFile base destructor. These additional complete decodes and the vtable entry are retained in build/009cdb90-resume/decoded-additional.log. The 123-byte resize callee at RVA 0x009CD890 takes an unsigned count and a four-byte owning value, uses an unsigned comparison, releases that parameter and returns with `ret 8`. The complete 74-byte sort driver at RVA 0x009CDB40 takes two pointers and a stack-slot comparator token and leaves cleanup to its caller. Its pointee width comes from its arithmetic; the owning string value evidence comes from the actual construction and copy helpers above. The full 61-byte copy helper is cdecl with first, last, output, iterator-tag reference and type-tag pointer; its complete calls and both return paths agree with the target's stack cleanup.

Retail has five unwind states. The compiled object's FuncInfo and unwind actions were decoded separately. Predecessors and receiver offsets agree: state 0 cleans the second string parameter at EBP+8 and goes to -1; state 1 cleans the first string parameter at EBP+4 and goes to 0; state 2 cleans the filename set at EBP-0x18 and goes to 1; state 3 cleans the temporary empty string at EBP-0x28 and goes to 2; state 4 cleans the vector at EBP-0x24 and goes to 2. The resize callee independently owns and destroys its by-value string parameter. The set cleanup route 0x00016CD4 to 0x001991E0 to 0x00197AE0 reaches the same destructor as normal cleanup through 0x000124DB. Its recursive erase at RVA 0x00195A50 destroys the node value at offset 0x10 through AsciiString's destructor before freeing the node. Vector cleanup uses the same complete destructor on normal and exceptional paths.

Retail unwind output is build/009cdb90-worker/eh-009cdb90.log and build/009cdb90-worker/eh-009cd890.log. The compiled metadata, cleanup disassembly and all parent relocation names are retained in build/009cdb90-worker/object-audit.log, with the original object retained as build/009cdb90-worker/verified-object.obj. A different cleanup offset, predecessor, element destructor or ownership route would refute exception correctness even if the ordinary body still matched.
