## Reproduced mismatch and rejected hypotheses

The saved body compiles to 249 bytes with nine relocation sites and 12 differing nonrelocation bytes. At offsets BA through BD, C3 through C6 and EC through EF, retail emits MOV ECX,EDI before PUSH 5 or PUSH 1. The bank emits the corresponding PUSH before MOV ECX,EDI. The active branch's PUSH followed by MOV sequences at offsets 7D and 86 already agree with retail. Thus the 45 missing or differing bytes measured over the 282-byte ledger span consist of the 12 setup bytes and the 33 unclaimed padding bytes. The explicit 249-byte comparison is in baseline-249.log.

The new hypothesis was that native declarations, getter structure, temporary lifetime, complete inline regions or actual callee visibility could expose an evaluation dependency missing from the bank. Identical instruction order after the relevant transformation refutes that individual lever. Prior verdicts were read in session-target.log, including the existing receiver, reference, member-pointer, fastcall, wrapper, flag-tail, barrier and compiler-flag trials. Those verdicts do not prove that all possible C++ source forms are exhausted.

Canonical Object declarations, unsigned frame counts, an inline Object getter, the actual ObjectModule base and getter, a Drawable base derived from Thing, drawable flag getters by value and reference, and containment getters by value and reference retain the same 249-byte body and 12 setup differences. Moving the initial boolean definition produces 19 differences. Factoring either complete state arm into a forced inline member, or both arms together, retains the 12 differences. An ordinary inline restore member is not inlined and produces a shorter caller. The raw logs use the corresponding canonical-object, unsigned-frame-count, object-getter, getter-boolean-lifetime, native-object-module-base, qualified-native-object-getter, drawable-thing-base, flag-bool-accessor, flag-reference-accessor, containing-object-accessor, containing-object-reference-accessor, restore-inline, restore-forceinline, enter-forceinline and both-state-helpers filenames.

Trivial receiver wrappers, an empty receiver destructor, a user-defined copy, and an implicit pointer conversion all retain the same 12 differences. Both already matched fade definitions were made visible together as inline noinline members, then the actual shadow setter was included with them. These three visibility trials retain the same 12 differences. Timer accessor layers change earlier register assignments and increase the mismatch to 17 differences while preserving the three setup swaps. A one-pass do block and redundant receiver null guards are neutral. Counted restore loops produce larger bodies and are rejected. ## Identity limitation and reopening condition

The oracle API was called with the actual body RVAs. It confirms the existing setShadowsEnabled and isLocallyControlled names and contradicts the inherited bfmeSyncEGF, bfmeInit962, bfmeGo1057A and ObjectAttemptDamageFlagHook::value decorations. The first three contain invented Bfme tokens; they were retained as the assignment requires. No new or changed real name, production source, ledger row, shared header or pin is introduced. The landed sibling's similar active predicate supplies layout context, not independent method-name proof.

The remaining blocker is the measured call-setup order. Reopening needs an independently supported source or compiler-context difference that changes one of these three sites without changing the body elsewhere, or an explicitly authorized assembly treatment of that isolated scheduling residue. Nothing in this note establishes that no clean C++ spelling can recover it. A successful byte comparison would still need opaque or independently proven identities and a complete indirect-call ABI review before collection.
