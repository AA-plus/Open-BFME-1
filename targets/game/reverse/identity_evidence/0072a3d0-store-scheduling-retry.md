## New hypotheses and measured refutations

The first hypothesis was that the map getter's narrow return representation might constrain scheduling. The actual inlined getter loads AX, merges with an EAX-zero fallback, then zero-extends AX before fild. Widening its C++ return to Int preserves the numerical range and tests whether the representation rather than the map element changes scheduling. The predicted improvement was a delayed final store with the earlier byte stream retained. Instead, the compiler replaced the narrow loads with movzx and regressed. This supports retaining the bank's unsigned-short getter.

The next hypothesis was that sequencing the final p2.Z assignment in the first triangle-call argument could delay the store until the scalar arguments were prepared. All arguments are side-effect-free apart from that local assignment, and the callee receives the same pointers and values. The hypothesis was refuted by an identical instruction result. /Op tested whether consistent floating-point rounding supplied the missing context; its extra rounding stores contradict retail and regress the body. Finally, a volatile access to only the final local Z field tested the documented use of volatile accesses for MSVC x87 scheduling. It also produced the identical instruction result. No volatile change was banked.

The store-family generator produced only swaps of the initial left/right integer coordinates, already inside the matching prefix; those choices do not address this divergence and were retained in store-choices.json without applying them. No old map caching, index precomputation, Vector3::Set, processor-tuning, direct-intersection or full-helper-visibility experiment was repeated.
