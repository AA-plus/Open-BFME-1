# Callback registration retry

The supplied Open BFME 2 donor is `Code/Libraries/Source/WWVegas/WWLib/stlport_ios_base_iword.cpp`, whose selected function at game.dat RVA `0x0001C010` is `pword`. It is a different method from this target. BFME 1 already has the corresponding `pword` body at RVA `0x0083F140`. The donor supplies the failure-reporting expression and compiler flags, but it does not supply a matched callback-registration counterpart. A source definition of `register_callback` in that donor would refute this screening correction.

The complete target decodes to 132 bytes. Its success path ends at RVA `0x0083F210` with `ret 8`, and its failure path ends at RVA `0x0083F241` with `ret 8`. Every conditional branch remains within the body. The receiver arrives in ECX. The first argument is stored in record field zero, and the second four-byte argument is stored in record field four. The target passes the callback pointer at receiver offset `0x24`, capacity at `0x28`, and used count at `0x2c` to the actual helper at RVA `0x0083EF20`.

The entire 147-byte grow helper was decoded, including its three returns. It doubles capacity or selects the required capacity, calls imported `realloc`, initializes both four-byte fields of each new eight-byte record, and writes the returned pointer and capacity into caller-supplied storage. It receives that storage as its first explicit cdecl argument and returns the same pointer in EAX. There is no compiler-generated hidden pair return in this declaration. The destructor at RVA `0x0083F730` and `imbue` at RVA `0x0083EC50` independently load record field zero as an indirect function pointer and field four as the integer argument. They pass an event, the same receiver, and that integer, then clean twelve argument bytes. This establishes the payload from actual field accesses rather than its allocation size. STLport 4.6's `_ios_base.h` declares the same callback signature and stores a pair of that function pointer and an integer.

The failure path reads state at receiver offset `8` and the exception mask at `0x14`. The image import directory identifies IAT VA `0x013593C8` as `MSVCR71.dll!fputs`. Its string is `ios failure`, and its stream is the imported `_iob` base plus `0x40`, agreeing with the matched BFME 1 `iword`, `pword`, and failure-reporting bodies. The donor trial uses the native stdio declarations. No new call or data pins were needed. No named direct caller was found by `callers_of.py`; that result is not an independent identity proof. The existing bank's method and field names are retained.

The cleaned saved body emits 132 bytes with three differences at `+0x66`, `+0x6c`, and `+0x6e`. Retail selects EDX for the stderr pointer while the compiler selects ECX. Making the complete grow definition visible with an inline noinline definition leaves the same three target differences. That copied helper emits 160 bytes against 147, so it is rejected as helper evidence. Applying the donor's `/Ob0 /MD` flags and `fputs("ios failure", stderr)` also leaves the same three target differences. Both scoped candidate gates fail with those three resolved differences and no unresolved references. Further unchanged register experiments were stopped. Reopening requires a new explanation for why retail keeps the stderr pointer in EDX after this exact success path.
