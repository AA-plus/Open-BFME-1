# Dependency-check donor port

Tested revision: `5345c7c3e1d23869406c66dc68b5774a110da8ee`, with this port applied in the working tree. Open BFME 2 donor `Code/Libraries/Source/Apt/Rva006D0C60.cpp` at game.dat `0x006D0C60` is a 266-byte near twin. Its source was read directly. The new hypothesis was that its table accessor and named missing-result temporary, combined with the currently landed owning lookup, would correct the bank's call-setup and pool-release register differences. A complete adapted source no closer than the 295-byte bank refutes that hypothesis. Both the adapted donor and its canonical-lookup variant instead reproduce all 294 BFME 1 bytes outside relocation operands.

The original method spelling is unknown. The saved `Rva00895B20::method(Rva00895B20Ref)` address identity is retained. The full caller at `0x008965B0` supplies the manager receiver in ECX, copy-constructs a one-pointer owning argument by incrementing its first dword, tests AL after the call, and receives `ret 4` cleanup. The method is a dependency check because it visits each leading C-string in the referenced object's table, constructs a pooled-string key, and returns false if its owning lookup is null. The donor's original class and method names are not promoted.

Complete target decoding covers `0x00895B20` through `ret 4` at `0x00895C43`, followed by INT3 padding. Every branch and jump remains within these 294 bytes. The referenced payload's table is at offset `0x10`. The table has a signed count at `0x28` and records pointer at `0x2C`. Every record is sixteen bytes with its name pointer at zero. The complete target and lookup establish these accesses; allocation size is not used as record-type evidence. The incoming handle and returned lookup handle own a payload whose dword reference count is at zero and whose complete landed destructor and sized free establish the 24-byte layout. Its pooled string uses a separate word reference count.

The complete 125-byte `BfmeStrVKI::bfmeSetVKI` consumes a C-string pointer with `ret 4`, creates or retains a pooled string, stores word length and capacity, and initializes the remaining word flags. The complete 22-byte `EAStringC` destructor decrements the word count and calls the allocator's second slot at zero. The native temporary uses exactly that storage and release operation. No EAStringC shared header is registered. The complete 163-byte `Rva00893030Manager::rva00895950` and its complete 115-byte `find008958D0` helper return a one-pointer owning handle in hidden storage, leave that address in EAX, consume hidden storage plus key with `ret 8`, and increment the payload count for a nonnull result. The port calls that already-landed declaration instead of adding a callee alias pin.

Retail unwind states are zero to -1 for the incoming handle at EBP+4 and one to zero for the EAStringC temporary at EBP-0x18. The emitted COFF reproduces those predecessor states and receiver offsets. Retail handle cleanup reaches the fully decoded 35-byte `Rva00784A70Cleanup`, whose decrement and drop helpers are twelve and thirty bytes; their complete bodies confirm null checks, dword release, payload destruction and size-24 free. Both string cleanup routes release the word count through the same pool slot. The temporary returned handle is released before the string, without adding an unwind state. The target has no virtual call; its indirect frees use the observed caller-cleaned four-byte and eight-byte argument lists.

The original bank emits 295 bytes with 101 non-relocation differences. Both the donor accessor and named result restore all 294 bytes. The final native-lookup trial and strict verifier pass all body bytes and REL32 targets; DIR32 consistency reports three symbols with zero new names. The EH generator stops on its exact baseline. ILT checking reports UNTESTABLE for this library body, so the opaque identity is retained without claiming an exported name.

Raw probes, complete target/caller/helper decoding, checked callee inventories, retail and emitted EH metadata, strict byte verification and immutable trial sources are retained under `build/donor-ports/00895b20-*`; the EH generator's receipt and original candidate are under `build/shape_search/74beefac10e04fbeb771a52d2166e87e/`.
