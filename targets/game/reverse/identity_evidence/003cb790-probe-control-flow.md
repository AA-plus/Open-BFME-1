The candidate recovers the complete 334-byte body under the bank's existing address-derived name, `Gen003BFB20Owner::probe(void *)`. ## New hypothesis and measurements

The original bank emits 334 bytes with 20 differences. Complete decoded instructions refute the earlier claim that every difference is a register swap. The branch displacement bytes at +0x064 and +0x07B send retail's empty-vector and unsuccessful-search paths to +0x0AD. The bank sends both paths to +0x09B and therefore calls `removeEntry` without erasing an entry. Moving that call into the successful erase block corrects these two bytes and leaves 18 register bytes. The hypothesis that this scope correction alone fixes allocation is refuted by that measurement.

The remaining differences are the receiver/result ESI and EDI exchange at byte offsets +0x01D, +0x024, +0x026, +0x037, +0x03D, +0x046, +0x055, +0x058, +0x068, +0x06D, +0x070, +0x080, +0x098, +0x09C, +0x0BA, +0x0C8, +0x0CF and +0x0D1. The audited candidate uses the actual member lookup contract, canonical named callees through inline forwarding helpers, the canonical AsciiString header and three distinct canonical globals. That combination emits the retail register assignment. Its first version emits one extra byte because native `getLength()` materializes the 16-bit length as an integer. The bank's borrowed header view instead performs retail's direct 16-bit comparison. Restoring that access makes all 334 bytes equal outside relocation operands. The integer return/storage view for `bfmeMakeBNG` also preserves that equality. The individual contribution of each forwarding helper to allocation has not been isolated.

The bank's one `TheLivingWorldCampaignManager` declaration represented both retail slots 0x012F1028 and 0x012F1024. The recovered source references `TheLivingWorldLogic` for the +0xA0 update and `TheLivingWorldCampaignManager` for selection. `TheLivingWorldManager` supplies the removal receiver at 0x012F706C. These are the canonical definitions in `data_rows.csv`; the source adds no global address literal or pin.

## Refutation and acceptance

A target branch leaving the extent, a caller that supplies a different receiver or argument contract, a copy helper accessing another value field, a different unwind cleanup receiver, or a scoped gate rejecting any relocated operand would refute this recovery. A relocation-masked exact result alone is not the acceptance check. The final scoped gate and naming checks are recorded separately in the worker's raw logs before collection.
