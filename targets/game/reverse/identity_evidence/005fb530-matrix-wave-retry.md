## Hypothesis and independent evidence

The retry hypothesis was that the complete decoded target uses different matrix accumulation grouping and coordinate lifetimes from the saved body. Retail evaluates the last two products before adding the first product in its first two matrix components. The canonical Matrix3D header inlined a different grouping into the saved attempt. A caller-local forceinline implementation with the witnessed grouping should preserve the matrix arithmetic prefix; a measured candidate with unchanged or worse instruction alignment would refute that experiment. It improved the measured candidate. The subsequent nested wave expression and native common return experiments also improved alignment. These are explicit C++ experiments, not a claim that a donor name proves the original source type.

The current neighbouring sources were read: colmathsphere.cpp and matrix3d.h for inverse transformation, Rva005FB4D0Link.cpp for the native handle return, LightningEmissionModuleCtor.cpp for module construction and the primary table, and fx_particle_system_bulk.cpp for the emission template records. The canonical coordinate declarations and their provider implementations were read in coord3d.h, coord3d.cpp, ActionManagerCanDoSpecialPower.cpp and BridgeBehaviorHandleObjectsOnDie.cpp. The Zero Hour particle and coordinate source was inspected; no corresponding lightning body was found, so this body is not a Zero Hour port. No earlier missing declaration was repaired by a new pin. The useful additional evidence is the complete native handle, coordinate copy, random helper and matrix decoding combined with these existing declarations.

## Lifetime and cleanup checks

Retail has two unwind states. State zero rolls back the static guard bit. State one destroys the native handle through the unlink route, with receiver adjustment LEA ECX,[EBP-0x50]. The candidate has the same state count and predecessor states, identical cleanup opcode bytes with relocations masked, the same guard symbol for both accesses, and the same destructor relocation and receiver adjustment. Raw metadata and comparison output is build/retry-005fb530/candidate-eh.log. This comparison verifies the unwind map and cleanup actions; it does not establish the original source-level class name.

Static storage contains thirty twelve-byte coordinates. Constructor thunk 0x00016C93 reaches the complete three-byte empty constructor at 0x00083330; destructor thunk 0x0001364C reaches the one-byte empty destructor at 0x0005BC40. The initial three-byte destructor display included two padding instructions, and the corrected one-byte extent was separately checked. The registered teardown at 0x00C70890, construction iterator at 0x009F6EE4, construction cleanup at 0x009F6F2E, destructor iterator at 0x009F6D76, its cleanup at 0x009F6DBE and array unwind helper at 0x009F6D18 were decoded and checked in full. The iterators pass each element in ECX to the actual constructor or destructor callback, advance or retreat by the recorded stride, and unwind the constructed or remaining prefix. All their return paths and internal branches are included in the boundary audit. These records establish the empty element destruction and the handle ownership independently of the matching main-body prefix.

Five existing coordinate definitions copied into the candidate passed scoped strict byte checks: the empty constructor and destructor, Coord3D copy constructor, Coord3D assignment and normalize. Their string and constant reference checks passed; the two global references matched the recorded DIR32 names. Raw output is build/retry-005fb530/proven-helper-byte-gate.log. The Coord3DBase constructor did not pass: its private raw-copy spelling adds register preservation in the standalone definition. Changing it to the canonical scalar provider worsened the caller; memcpy produced the same caller and the same failing standalone helper. Both rejected sources and raw outputs remain in build/retry-005fb530/37-canonical-base-constructor.cpp and 38-base-memcpy.cpp with their probe logs and 38-helper-byte-gate.log. No copied helper is offered as a new recovery.
