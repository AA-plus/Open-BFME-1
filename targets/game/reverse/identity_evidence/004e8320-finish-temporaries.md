# grabSinglePlayerInfo temporary and scheduling audit

The tested base is 4db97d5ccf56b971c8d4de3e44279a5c05fed18d. The original bank emits 1,036 bytes with 69 non-relocation differences. The preserved reconstruction emits 1,036 bytes with 24 differences, and strict relocation resolution reports the same 24 differences with no unresolved calls. This is a partial reconstruction. The dump row remains the production provider, and no recovered bytes are claimed.

## Retry hypothesis and falsification

The earlier records cover scratch-register sweeps, adjacent stores, reversed score updates, helper visibility and several individual getter temporaries. The new hypothesis was that the remaining scheduling reflected the lifetimes of multiple accumulated results and the side-image/color outputs together. Retail loads a building-loss value before storing the destroyed-building total, delays other scalar stores, and loads color before storing the side image. A candidate that retained these lifetimes but reproduced the original instruction and relocation result would refute that particular experiment. The hypothesis produced measured improvements, so the earlier register-allocation label did not establish exhaustion.

Explicit image and final-unit-loss temporaries reduced the residue from 69 to 60 bytes. Staged money and unit values reduced it to 51 bytes. Keeping both building totals in temporaries and delaying the building-loss store reduced it to 31 bytes. Returning color from the force-inlined aggregation helper reduced it to 24 bytes. The preferred candidate keeps the existing descriptive names, uses unsigned Color and the canonical const-qualified Player::getRelationship declaration, removes the artificial volatile units-built read, and retains the Zero Hour body comments.

## Complete boundary and identity

Retail code ends with RET at +0x3F3. Its six switch-table entries occupy +0x3F4 through +0x40B and contain image addresses 0x008E8426, 0x008E8434, 0x008E8442, 0x008E8421, 0x008E842F and 0x008E843D. Subtracting the image base places every entry on a decoded instruction inside this function. INT3 starts at +0x40C. The complete extent is therefore 1,036 bytes, consisting of 1,012 code bytes and 24 table bytes. The code portion has one return path and no direct conditional branch or tail jump outside that portion. The indirect switch dispatch uses exactly the six verified entries.

The complete 1,036-byte checked_callees request fails because its linear decoder treats table data as instructions and stops at 0x004E8727. The 1,012-byte code request succeeds. The probe's six misaligned relocation reports are exactly the six DIR32 table entries at +0x3F4, +0x3F8, +0x3FC, +0x400, +0x404 and +0x408. They are not shifted call operands. The screening claim of an installed 0x00FFFFFF vtable is also refuted: that value initializes color.

The complete decoded initSinglePlayer body calls ILT 0x000077C5 at 0x004E8936, and the complete initReplaySinglePlayer body calls it at 0x004E89CA. Neither site passes arguments or supplies hidden return storage. Their matched C++ sources name grabSinglePlayerInfo. The ILT routes to 0x004E8320, and ilt_oracle.check on the body RVA confirms ?grabSinglePlayerInfo@@YAXXZ. These facts support the free cdecl void() identity independently of this partial's byte score. A decoded route or caller ABI disagreement would refute it.

Player::getNthPlayer is decoded completely through both RET 4 paths and uses a signed 32-bit index. Player::getRelationship is decoded through both RET 4 paths and returns a 32-bit Relationship; its canonical const decoration is oracle-confirmed. The single-player flag helper is decoded through both returns and produces boolean zero or one. The target separately reads the Player observer/list bytes through their actual helper calls.

The ScoreKeeper receiver is Player +0x348. The target's scalar reads establish money earned at ScoreKeeper +0x04, money spent at +0x08, units built at +0x8C, units lost at +0x90, buildings built at +0x114 and buildings lost at +0x118. Both complete 40-byte destroyed-total helpers read all 32 dwords from +0x0C or +0x94, using eight unrolled four-element iterations; their canonical native source declares these counters as Int. They return the sum in EAX, preserve the saved registers and use plain RET. The native donor helper bodies were inspected, compiled beside the new pipeline as inline noinline copies, and each separately matched all 40 bytes. Their visibility leaves the caller residue unchanged.

The complete populateSideInfo consumer reads all eight 32-bit ScoreGather counters at +0x00 through +0x1C and the non-owning image pointer at +0x20. Its declaration uses unsigned Color, whose decoration is oracle-confirmed. No STL key or payload inference is needed for this target. The complete PlayerTemplate::getSideIconImage helper takes the address of its AsciiString at +0xE0, forwards it to the image lookup, and returns an Image pointer in EAX. The complete image lookup consumes a string reference and returns an image pointer or zero through RET 4 paths. The bank's inherited MappedImageCollection view and pin spelling are retained; the canonical callee owner in the ledger is ImageCollection, and this partial does not assert a separate collection identity.

The indirect GameText call at target +0x393 uses vtable slot +0x24. Its complete 114-byte AsciiString overload takes hidden UnicodeString result storage, a four-byte nontrivial AsciiString value, and a Bool pointer. It forwards to the char overload, releases the incoming narrow string, returns the hidden result address in EAX, and ends with RET 12. The target then passes the returned UnicodeString value, ScoreGather pointer, position and Color to populateSideInfo and cleans 16 bytes. This agrees with the canonical declarations and distinguishes return storage from an ordinary scalar argument.

The retail unwind map has state 0 to -1 for side at EBP -0x44 and state 1 to 0 for label at EBP -0x48. Both actions route to the narrow-string destructor. The candidate compiler listing has the same two predecessors and offsets. The complete narrow copy helper copies the sole data pointer and increments the referenced buffer's refcount; the complete release helper decrements that count, frees the buffer only at zero and clears the pointer. The caller owns side and label. The copied AsciiString argument is destroyed by GameText::fetch, and the returned UnicodeString argument is consumed by populateSideInfo. No array or member-object cleanup is introduced by the new scalar temporaries.

## Remaining mismatch

All 24 strict differences are at +0x249, +0x24F, +0x259, +0x25D, +0x266, +0x26A, +0x276, +0x278, +0x27D, +0x27E, +0x27F, +0x281, +0x282, +0x283, +0x284, +0x285, +0x2BF, +0x2C4, +0x2C5, +0x2C6, +0x2C7, +0x2C8, +0x2D3 and +0x2DD. The first eight concern scratch registers in the buildings-built and destroyed-building updates. The next eight concern the order and registers of the destroyed-building store and building-loss addition. The next six concern the last unit-loss load/addition and the template receiver load. The final two use EBP for color where retail uses EDX. No difference lies in a relocation operand or outside these decoded instructions.

The session tested canonical declarations, embedded/member-based views, native StringBase declarations, scalar signedness, native helper visibility, exception specifications and mode, compiler tuning, helper interfaces, return values, local lifetimes, grouped values and results, early-continue filters and relationship forms. Finite searches additionally tested 24 scalar update orders, 30 delayed-store combinations, 30 staged-value orders, 25 building-result pipelines, result forms, output forms and 180 placements of the delayed building store among money and unit updates. The 180-case search leaves the 24-byte candidate best. A few failed scope variants do not count as evidence about compiler output, and two initial relationship trials whose replacement did not apply were excluded; their corrected trials are retained separately.

This does not prove an assembly requirement. Reopening is justified by a new source lifetime, declaration or native helper contract that predicts a change in one of the remaining decoded groups. Repeating the exhausted register/store spelling sweeps without such a prediction is not justified. The preferred body and all unedited trial probes remain available for reproduction.
